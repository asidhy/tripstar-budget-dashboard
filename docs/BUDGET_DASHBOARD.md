# 预算看板（Budget Dashboard）特性说明

> 本文件记录在 TripStar 上新增「预算看板」特性的实现方案与验收方式。
> 对应赛题：**赛题 2 · AI应用开发-部署旅游应用增量开发预算看板特性**。

## 一、需求

TripStar 原本只有「预算明细面板」，展示的是**规划阶段的预估花销**（门票/住宿/餐饮/交通的合计）。
它回答不了旅行中真正会问的问题：**实际花了多少？超没超？谁该给谁钱？**

因此新增「预算看板」，补齐四件事：

| # | 能力 | 说明 |
|---|------|------|
| 1 | 预算与实际支出对比 | 预算总额 vs 已录入实际支出，进度条 + 剩余/超支金额 |
| 2 | 分类占比 | 景点门票 / 住宿 / 餐饮 / 交通 / 其他 五类，各自的预算与实际双向对比，以及占总支出的比例 |
| 3 | 每日支出趋势 | 按行程天数聚合，柱状图展示每天花多少，找出花钱高峰日 |
| 4 | 成员分摊与结算建议 | 每笔支出记录付款人与参与分摊成员，按「已付 − 应摊」算净额，再用贪心配对给出最少转账笔数的结算方案 |

## 二、实现方案

### 2.1 改动清单

| 文件 | 类型 | 说明 |
|------|------|------|
| `frontend/src/components/BudgetDashboard.vue` | 新增 | 预算看板全部 UI 与逻辑，约 700 行，自包含 |
| `frontend/src/views/Result.vue` | 修改 | ① 顶部导航菜单新增「预算看板」入口 ② 渲染 `<BudgetDashboard>` 区块 ③ 引入组件 |

**没有新增后端接口。** 理由见下节。

### 2.2 为什么不需要后端接口

预算基线（`TripPlan.budget`）本来就在行程数据里，由后端规划 Agent 生成并随 `TripPlan` 一起返回，前端已经拿得到。
实际支出是**用户自己边玩边记的**，属于个人本地数据，不需要多端同步，也不该进服务端数据库。

所以采用 `localStorage` 持久化，键名 `tripstar-budget-dashboard-v1:<planId>`，按行程隔离：
换一个行程就是一份独立的账本，刷新页面不丢数据。

### 2.3 数据结构

```ts
interface Expense {
  id: string
  title: string              // 支出名称，如「兵马俑门票」
  category: 'attraction' | 'hotel' | 'meal' | 'transport' | 'other'
  amount: number             // 金额（元）
  dayIndex: number           // 属于第几天，1 起
  paidBy: string             // 谁付的钱
  sharedBy: string[]         // 这笔钱由谁分摊
  createdAt: number
}
```

### 2.4 预算基线映射

`TripPlan.budget` 的字段直接映射到五个分类：

| 分类 | 预算来源 |
|------|----------|
| 景点门票 | `budget.total_attractions` |
| 住宿 | `budget.total_hotels` |
| 餐饮 | `budget.total_meals` |
| 交通 | `budget.total_transportation + budget.total_inter_city_transport` |
| 其他 | 无预算（`0`），只有实际支出时才有数据 |

### 2.5 结算算法

对每个成员 `m`：

```
paid(m) = Σ 所有 paidBy === m 的支出金额
owed(m) = Σ 所有 m ∈ sharedBy 的支出金额 / |sharedBy|
net(m)  = paid(m) - owed(m)      // > 0 应收，< 0 应付
```

然后用贪心配对把净额抹平：债权人按金额降序、债务人按金额降序，每次取 `min(应收, 应付)` 生成一笔转账，
直到一方清零。这样给出的结算方案**转账笔数最少**，不会出现 A→B→C 的绕圈转账。

### 2.6 图表

用项目已有的 `echarts`（`frontend/package.json` 已依赖 `^5.5.1`），没有引入新的图表库：

- 每日趋势：柱状图，渐变填充
- 分类占比：环形饼图，分类色与左侧对比条一致

## 三、验收方式

1. 起服务：`cd frontend && npm install && npm run dev`，浏览器打开 `http://localhost:3000`
2. 生成任意一份行程，进入结果页
3. 顶部导航点「**预算看板**」
4. 逐项自检：

- [ ] 顶部四个指标（预算总额 / 已支出 / 剩余预算 / 预算使用率）有数，且使用率超过 100% 时变红
- [ ] 分类预算对比：五类都有「实际 / 预算」与两条叠加进度条，超预算的那类变红
- [ ] 每日支出趋势：柱状图天数与行程天数一致
- [ ] 支出分类占比：环形图能显示各分类比例
- [ ] 成员分摊：每人显示「已付 / 应摊 / 应收或应付」
- [ ] 结算建议：给出 `A → B ¥xx` 形式的转账清单，且金额之和与净额自洽
- [ ] 记一笔支出后，以上所有数字与图表**实时联动更新**
- [ ] 刷新页面后，刚才记的支出还在（localStorage 生效）
- [ ] 点「恢复初始数据」能重置回按行程预算生成的初始记录

## 四、设计取舍

**不做的事**：没有把实际支出写回后端 `TripPlan`。
因为那会让「规划结果」变成可变状态，与 TripStar「一次生成、可导出分享」的产品定位冲突；
预算看板定位是**用户自己的账本**，与行程数据解耦更合理。

**已知边界**：支出记录只在当前浏览器可见，换设备不同步。若后续要做多端同步，
再在 `backend/app/api/main.py` 增加 `/api/trips/{plan_id}/expenses` 增删查接口即可，前端只需替换 `loadState/saveState` 两个函数。
